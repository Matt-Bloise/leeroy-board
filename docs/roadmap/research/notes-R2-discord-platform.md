## 1. Discord Activities (Embedded App SDK)

### 1.1 What an Activity is, lifecycle, launch
| Fact | Source | Label |
|---|---|---|
| An Activity is a web app in an iframe that talks to the Discord client through the Embedded App SDK over `postMessage`. Runs on desktop, mobile, web. | https://docs.discord.com/developers/activities/overview , https://docs.discord.com/developers/activities/how-activities-work | confirmed |
| Lifecycle: iframe loads with query params; SDK constructor starts a handshake; `ready()` resolves on READY; app then calls `authorize` (gets code), exchanges the code on its own server, calls `authenticate`; commands/events need granted scopes; Discord may send CLOSE; app can send CLOSE. | https://docs.discord.com/developers/activities/how-activities-work | confirmed |
| SDK is meant for single-page apps; a full page reload can leave `ready()` never resolving (open issue #41). | https://docs.discord.com/developers/activities/how-activities-work ; https://github.com/discord/embedded-app-sdk/issues/41 | confirmed (docs) / likely (issue) |
| The SDK constructor throws unless `frame_id`, `instance_id`, `platform` query params exist. Optional: `guild_id`, `channel_id`, `location_id`, `custom_id`, `referrer_id`, `mobile_app_version`. | Once the SDK is added, the Activity cannot be viewed in a normal browser. | https://docs.discord.com/developers/activities/building-an-activity | confirmed |
| Launch routes: (a) the app's Entry Point command in the App Launcher, (b) responding to a command, component or modal-submit interaction with callback type `LAUNCH_ACTIVITY` (12). | https://docs.discord.com/developers/activities/how-activities-work , https://docs.discord.com/developers/interactions/receiving-and-responding | confirmed |
| Entry Point command: type `PRIMARY_ENTRY_POINT` (4), global only, exactly one per app, `handler` 2 = `DISCORD_LAUNCH_ACTIVITY` (Discord launches and posts a follow-up message) or 1 = `APP_HANDLER` (your server handles it, then may reply with type 12). | Instance: `discordSdk.instanceId` is available at construction. Everyone who joins the same running application gets the same id. | Participants: `getActivityInstanceConnectedParticipants()` and event `ACTIVITY_INSTANCE_PARTICIPANTS_UPDATE`. Old name `getInstanceConnectedParticipants` renamed Oct 6, 2026, removal in a future major. | multiplayer-experience page above ; https://docs.discord.com/developers/change-log | confirmed |

**Design implication (inference, speculative as design advice):** because instances die when the last person leaves, all durable party/raid state must be keyed by `guild_id` (and your own party id) in D1 or a Durable Object, never by `instance_id`. Use `instance_id` only for live presence.

### 1.2 Identity the SDK gives you
- `authorize({client_id, scope[], response_type:'code', prompt:'none', state?, code_challenge?, code_challenge_method:'S256'})` returns a `code`. The SDK request type accepts a PKCE challenge. Source: https://docs.discord.com/developers/developer-tools/embedded-app-sdk . **confirmed**.
- Your server exchanges the code at `https://discord.com/api/oauth2/token` (needs client secret unless public client), then client calls `authenticate({access_token})`. Response: `access_token`, `user`, `scopes`, `expires`, `application`. Source: building-an-activity and SDK reference pages. **confirmed**.
- Tutorial scopes: `identify`, `guilds`, `applications.commands`. Add `guilds.members.read` for the user's roles/nick in the current guild and for `getChannelPermissions()`. `rpc.activities.write` for `setActivity`; `rpc.voice.read` for voice events. `dm_channels.read`, `relationships.read` need Discord approval. Source: SDK reference scopes table. **confirmed**.
- Trust rule: treat everything the client reports (user, Nitro, channel) as untrusted; query Discord from your server with the user's OAuth token for trusted data. Sanitize usernames with `.textContent`. Source: https://docs.discord.com/developers/activities/development-guides/networking . **confirmed**.
- Tokens: treat access and refresh tokens like passwords; store encrypted (tutorial). Token lifetime in examples 604800 s (7 days). **confirmed**.
- To get guild roles of all participants, the SDK only exposes the current user's guild member; the docs say your server should fetch members for the rest. **confirmed**.

### 1.3 Mobile, portrait, layout
- Supported platforms are enabled per platform in the Developer Portal ("Supported Platforms"); an Activity only shows on a platform if that is enabled. HTTPS not required on mobile (required on web/desktop). Source: https://docs.discord.com/developers/activities/development-guides/local-development . **confirmed**.
- `setOrientationLockState({lock_state, picture_in_picture_lock_state, grid_lock_state})`: iOS and Android only (not web). Values UNLOCKED(1), PORTRAIT(2), LANDSCAPE(3), UNHANDLED(-1). Call after `ready()`. The Developer Portal can set a default lock (separate defaults for phones and tablets) that Discord applies before the SDK initializes, avoiding a visible rotation. Sources: SDK reference; https://docs.discord.com/developers/activities/development-guides/layout . **confirmed**.
- `ORIENTATION_UPDATE` event (screen orientation, may differ from physical orientation) and `ACTIVITY_LAYOUT_MODE_UPDATE` (FOCUSED 0, PIP 1, GRID 2); older clients only send `ACTIVITY_PIP_MODE_UPDATE`, SDK has compat subscribe helpers. **confirmed**.
- `THERMAL_STATE_UPDATE` (NOMINAL..CRITICAL) from iOS/Android. `getPlatformBehaviors()` exposes `iosKeyboardResizesView`. **confirmed**.
- Design-patterns page: keep controls out of notches/cutouts, curved Android edges, bottom swipe gestures and the Android back button; respect safe area; prioritize time-to-first-interaction; minimize WebAssembly (older iOS WebKit optimisation pass causes stutter and degraded AV); the Discord client shares CPU/RAM/GPU with your Activity; design for solo and 3-8 people but test 25+; usable in text channels without voice; TAB nav, ESC to close modals; avoid login walls early. Source: https://docs.discord.com/developers/activities/design-patterns . **confirmed**. The page does not mention portrait explicitly; portrait support comes from the orientation-lock API above.
- Known open SDK issues (point-in-time, from GitHub): black screen after an Activity closes on iOS and Android (#379), audio from other apps pauses when an Activity opens on iPhone (#380), Android PiP recreates the runtime and breaking re-init (#355), `ready()` never resolves when `user.avatar` is null on SDK 2.5.0 (#386). Source: https://github.com/discord/embedded-app-sdk/issues . **likely** (single-reporter issues, status not verified).
- Spotted a stale line: the design-patterns page still says monetization is "coming soon" although monetization docs are live and `startPurchase` exists. Treat that page as partly dated. **confirmed** (internal inconsistency).

### 1.4 URL mappings, proxy, CSP
- All traffic goes through the Discord proxy (runs on Cloudflare Workers). CSP restricts requests to your own `{clientId}.discordsays.com` and mapped targets; unmapped hosts fail `blocked:csp`. Full URL pattern `{protocol}://{clientId}.discordsays.com{path}`. Outbound destinations are Developer Portal URL Mappings (prefix to target, e.g. `/` to your Pages domain, `/api` to a Worker). Source: https://docs.discord.com/developers/activities/development-guides/networking . **confirmed**.
- `/.proxy/` prefix no longer required (July 30, 2025); SDK 2.2 `patchUrlMappings` omits it. `patchUrlMappings([{prefix, target}])` patches global `fetch`, `WebSocket`, `XMLHttpRequest`. Source: change log + networking page. **confirmed**.
- WebSockets are the only real-time transport; WebRTC unsupported; WebTransport pending. **confirmed**.
- Cookies: domain must be `{clientId}.discordsays.com`, `SameSite=None; Partitioned`. **confirmed**.
- Dev: tunnel (cloudflared) plus `/` mapping; if you use a tunnel domain you do not own, reset the mapping afterward. **confirmed**.
- Cloudflare fit (inference): Pages for static assets plus a Worker route mapped under the same discordsays.com host fits the model. `/api/token` code exchange belongs in a Worker. **speculative** (design inference).

### 1.5 Discoverability, verification
- Activities are Verified or Unverified. Unverified: visible only to the team and invited testers, not discoverable, and (per the Discord help article as quoted in search results) only launchable in servers with fewer than 25 members. Verified: open to all users, any server size, eligible for discovery and monetization. Source: https://support-dev.discord.com/hc/en-us/articles/26576097154199-What-are-Verified-and-Unverified-Activities (403 to my fetcher; text taken from search snippets; article ~551 days old at time of search). **likely**. Also Tutorial: "non-distributed Activities can only be launched by the app owner or developer team members" (https://docs.discord.com/developers/activities/building-an-activity , **confirmed**).
- Verification itself: the owner of the team must verify identity through Stripe; app must belong to a team; a checklist on the App Verification tab. Source: https://support-dev.discord.com/hc/en-us/articles/23926564536471-How-Do-I-Get-My-App-Verified (403; snippets only). **likely**. Bot verification is required to grow past 100 servers (snippets, same). **likely**; the gateway doc also states "Verification is required for apps in 100+ guilds" (https://docs.discord.com/developers/events/gateway , **confirmed**).
- App Directory: "your app needs to be verified and opted into discovery". Needs at least one tag (max 5) and "Enable Discovery" on the Discovery Status tab; apps must be suitable for 13+. It can take up to 30 hours for an Activity to appear in the search bar. Sources: https://docs.discord.com/developers/platform/discovery (verified+opt-in = **confirmed**); the tag/13+/30-hour details from support articles via snippets = **likely**.
- Activity age-restriction: since Sept 22, 2026 age-restricted Activities may require runtime age-group confirmation, no code changes. Source: change log. **confirmed**.
- Other discovery: App Launcher shows recently used and curated apps; others in the server can see apps used in-server and open the profile. **confirmed** (discovery page).

## 2. The ingestion problem (reading members' threads and forms)

### 2.0 Hard facts that frame every option
1. Without the Message Content privileged intent, `content`, `embeds`, `attachments`, `components` come back empty and `poll` is omitted. Exceptions (content still visible): messages the app sends, DMs to the app, messages that @mention the app, replies to the app's messages (when "ping on reply" is on), and the message targeted by a **message context menu command**. Source: https://docs.discord.com/developers/events/gateway and https://docs.discord.com/developers/gateway/you-might-not-need-a-privileged-intent . **confirmed** for gateway; the "you might not need" page says the same for received messages; the Message Content discussion says restriction covers fields "across Discord's APIs" so REST reads are very likely restricted too (https://github.com/discord/discord-api-docs/discussions/5412) . **likely** for REST. The message resource page links the restriction to the Gateway and does not say REST outright. Test this on your own bot before betting the design on it.
2. Privileged intents: `GUILD_PRESENCES`, `GUILD_MEMBERS`, `MESSAGE_CONTENT`. Toggle in Developer Portal. Apps with fewer than 10,000 users can enable them directly; above that, review and annual reconfirmation. Verification required in 100+ guilds; the gateway page also says verified apps must get each intent approved after verification. Unverified apps in fewer than 100 guilds need no approval. Sources: https://docs.discord.com/developers/events/gateway ; change log June 10, 2026. **confirmed**. The exact interaction between "verified" and "under 10,000 users" is ambiguous in the text (see Open questions).
3. Gateway limits: 120 sent events per 60 s per connection; payload max 4096 bytes; 1,000 IDENTIFY per 24 h globally (RESUME does not count); exceeding the IDENTIFY cap kills sessions, resets the bot token and emails the owner; one shard per 2,500 guilds. Close codes 4014 (unapproved privileged intent) and 4013 (invalid intent). Clean close with 1000/1001 invalidates the session. **confirmed**, same gateway page.
4. Thread facts: forum channel type 15; each post is a thread whose starter message has the same id as the thread; tags `available_tags` (max 20, name max 20 chars), `REQUIRE_TAG` flag (1<<4); posting to a forum needs only `SEND_MESSAGES`; archived threads must be unarchived to accept messages (sending unarchives); enumerate via `/guilds/{id}/threads/active` and `/channels/{id}/threads/archived/public` (needs `READ_MESSAGE_HISTORY`); `message_count`/`total_message_sent` are not updated via CHANNEL_UPDATE. Sources: https://docs.discord.com/developers/topics/threads , https://docs.discord.com/developers/resources/channel , https://docs.discord.com/developers/resources/guild . **confirmed**.
5. Forum posts have no native form fields. Structure comes only from required tags and post guidelines (channel `topic`, up to 4096 chars). **confirmed** for limits; "no native form fields" is my reading of the channel docs (**likely**).

### 2.2 Pitfalls for the Durable Object gateway pattern (option c)
Evidence: https://github.com/dcartertwo/discord-gateway-cloudflare-do (heartbeat on alarms, reconnect backoff 1 s to 5 min, 5 reconnects/60 s cap, resume with session id + sequence, stops on 4014, forwards only MESSAGE_CREATE and reactions as HTTP POST, 29 tests, MIT, 3 commits); https://github.com/cloudflare/awesome-agents/tree/main/agents/discord-agent (gateway DO sends heartbeats via alarm, must be started once after each deploy via `POST /start`); https://github.com/okou-ai/okou/issues/36643 (persist the outbox and resumable sequence in order before forwarding, stable event ids for idempotency, heartbeats must not wait on API calls, poison event handling, treat `GUILD_DELETE unavailable=true` as outage not uninstall, dead-letter store, no assumption that inbound hibernation covers the outbound socket); https://github.com/mizchi/discord-cf (explicitly "not ready for production", does not document keepalive). All **likely** for the pattern working, because they are community code, not vendor-supported.
Platform facts: outgoing WebSockets do not hibernate; an open outbound connection keeps the object in memory (docs say up to 15 minutes, may stay open longer); duration billing does not stop (https://developers.cloudflare.com/durable-objects/best-practices/websockets/ , **confirmed**). One alarm per object, at-least-once, 6 retries with exponential backoff from 2 s, then the alarm stops until you set one again (https://developers.cloudflare.com/durable-objects/api/alarms/ , **confirmed**). Alarm handlers have a 15 min wall limit (https://developers.cloudflare.com/workers/platform/limits/ , **confirmed**). Free plan DO: SQLite-backed only, 100,000 requests/day, 13,000 GB-s/day; paid 1M requests and 400,000 GB-s/month included, $12.50 per million GB-s extra (https://developers.cloudflare.com/durable-objects/platform/pricing/ , **confirmed**). The pricing page does not say how outbound WebSocket messages are billed as requests; the stated 20:1 ratio applies to incoming messages on a WebSocket connection. **speculative** whether gateway events count that way.
Protection from Discord's side: re-IDENTIFYing on every DO eviction burns the 1,000/day budget and can reset the token; the design must persist session id, resume URL and sequence and use RESUME (**confirmed** for the limit; the persistence advice is **likely**).

### 2.3 Recommended architecture (answer)
**Hybrid, in this order of build priority:**
1. **Interactions as the form layer (option a).** Replace "members fill out forms in Discord" with: a pinned bot message in each forum or channel with a **Submit build** button (type 2 component) that opens a modal (Label + Text Input + String Select + Radio Group), plus a **message context menu command** ("Import to Board") for threads members already wrote. Context menus give the full message content with no privileged intent. Interaction payload carries `member.roles`, so you also get the author's role set for free. Defer (type 5) immediately and finish the D1 write and any LLM parsing via `ctx.waitUntil`, editing the original response within the 15-minute token window.
2. **Cron REST poller for passive forum reading (option d)**, tighter than 6 h (every 5-15 minutes on the Paid plan; hourly on free). Incremental by snowflake: list active threads, compare `last_message_id` and `message_count` with D1, fetch only changed threads. Requires the Message Content intent to be toggled on the bot in the Developer Portal (free for an unverified bot under 100 servers), and `VIEW_CHANNEL` + `READ_MESSAGE_HISTORY` on the forum.
3. **Only if sub-minute latency is truly needed:** run the gateway on an OCI Always Free micro VM or a ~$2 Fly machine (option b) rather than a DO (option c), or use a DO gateway relay that only forwards thread ids and lets the poller fetch bodies. Rationale: option c is possible (Workers gateway block was lifted Dec 5, 2025 per a Discord contributor, https://github.com/discord/discord-api-docs/issues/6145 , **likely**), but it consumes ~83% of the paid DO duration allowance or ~85% of the free allowance for a single always-on object, with no vendor-supported library.

**What the bot needs**
- Install scopes: `bot` + `applications.commands` (https://docs.discord.com/developers/topics/oauth2 , **confirmed**).
- Intents (only if polling or gateway): `GUILDS` (non-privileged; thread create/update events), `GUILD_MESSAGES`, `MESSAGE_CONTENT` (privileged). Avoid `GUILD_MEMBERS`; use the interaction `member` payload, `GET /guilds/{id}/members/{user}` and OAuth `guilds.members.read` instead (the "you might not need a privileged intent" page lists these alternatives, **confirmed**).
- Channel permissions: View Channel, Read Message History, Send Messages, Send Messages in Threads, Embed Links, Use Application Commands; Manage Threads only if the bot must unarchive or lock threads; Manage Roles only to assign opt-in roles (and its role must sit above the roles it assigns, **likely**); avoid Administrator and Mention Everyone. Source for thread permission names: threads topic page, **confirmed**.

## 4. Identity: Discord OAuth2 as the site login

- Grants: authorization code, implicit (not recommended), client credentials. Scopes relevant: `identify`, `email` (adds email/verified to `/users/@me`), `guilds` (list with `owner`, `permissions`, `features`), `guilds.members.read` (member object in a guild), `connections`, `role_connections.write` (not with implicit), `bot`, `applications.commands`, `webhook.incoming`; `dm_channels.read`, `identify.premium`, `rpc.*`, `relationships.read` are partner/approval only. Source: https://docs.discord.com/developers/topics/oauth2 . **confirmed**.
- `GET /users/@me/guilds` returns up to 200 guilds (non-bot users can join at most 200), `with_counts` optional. `GET /users/@me/guilds/{id}/member` needs `guilds.members.read`. Source: https://docs.discord.com/developers/resources/user . **confirmed**.
- `state`: optional in Discord's docs, strongly recommended; validate on return. Authorization responses now carry `iss=https://discord.com` (RFC 9207, Oct 14, 2026). Token endpoints accept only `application/x-www-form-urlencoded`. Revocation at `/oauth2/token/revoke` revokes all tokens of the authorization. **confirmed**.
- PKCE: the docs recommend "authorization code grant with PKCE" for production but do not document parameters on the OAuth page; the Embedded App SDK `authorize` request does accept `code_challenge` + `code_challenge_method: 'S256'`. A GitHub release note and the Arctic library docs indicate PKCE works for public clients and requires enabling the "Public Client" toggle on the app's OAuth2 page. Whether PKCE can be combined with a confidential (secret-holding) client is unclear. SDK page **confirmed**; public-client toggle **likely**; combination **speculative / open**.
- Identity mapping (inference): use the Discord user snowflake (`id`) as the sole key of one site account. `username` is not unique (docs state this), `global_name` and avatar change. Do not use email. A site account owns N guild memberships (rows: guild_id, roles snapshot, last_verified_at). **speculative** (design) except the "username is not unique" fact (**confirmed**).
- Membership checks: at login, call `GET /users/@me/guilds` with the user's token (cheap, no bot needed) to learn which guilds contain the user and whether they hold ADMINISTRATOR/MANAGE_GUILD via `permissions`; for role-level authorization in a guild where your bot is installed use `GET /guilds/{id}/members/{user}` with the bot token (no intent needed, per the "alternatives" page) or `guilds.members.read`. Re-check on a short TTL, never trust Activity client data. **confirmed** for endpoints; policy is design.
- Tokens: access tokens 7 days (examples); store refresh tokens encrypted or do not store them if you only need a login proof; revoke on logout/uninstall; handle `APPLICATION_DEAUTHORIZED` webhook events and `invalid_grant` for out-of-band unlinking (change log May 22 and Sept 17, 2026). **confirmed**.
- One identity across surfaces: the Activity and the website both use the same OAuth app (same client id) so the same `user.id` appears. The Activity gets its token through `authorize`/`authenticate`; the site through a normal redirect flow with a registered redirect URI. **likely** (follows from the docs).

## Surprises versus what a team would assume
1. Discord's docs moved to docs.discord.com, and the policy, verification and help articles that matter most (Developer Policy, Terms, verification, Verified/Unverified Activities, Premium Apps Payout) are not fetchable by automated readers. Plan to read them in a browser.
2. An unverified Activity may be launchable only by team members/testers and only in servers under 25 members (snippet-sourced). A 40-player raid guild cannot be a pilot without verification.
3. Activity pages cannot run in a normal browser once the SDK is present, and instances die when the last person leaves. The website and the Activity need distinct entry points and guild-keyed storage.
4. `startPurchase` is web/desktop only; mobile Activity users cannot buy inside the Activity per the SDK table.
5. Premium Apps payouts are limited to US/EU/UK teams, require $100 earned, and Discord takes 15% of the first $1M (snippet-sourced).
6. A message context menu command gives your bot message content with no privileged intent, which is the cheapest legitimate way to ingest a specific thread post.
7. The Workers-to-gateway block (HTTP 401 in 2023) was lifted on Dec 5, 2025 per a Discord contributor, so a DO gateway is no longer impossible, but outbound WebSockets never hibernate, so it costs about 331,776 GB-s/month always-on (83% of the paid allowance) and nearly all of the free daily allowance.
8. Webhook events for apps contain no guild message, thread or forum events at all; they are for authorization, entitlements and Social SDK lobbies.
9. Workers share egress IPs, so Discord's Cloudflare-level 429/1015 bans hit Workers bots in 2024; staff said Nov 2025 it is resolved. Still add backoff.
10. Linked Roles are pull-only (each user must opt in) and capped at 5 metadata keys; they are not a broadcast mechanism.
11. The privileged-intent threshold is now framed around 10,000 users with annual reapplication (change log June 10, 2026), not only the old 100-guild rule.
12. The Activity design-patterns page still says monetization is "coming soon" while the monetization docs are live: some Discord pages lag.
13. Forum channels cannot enforce fields; REQUIRE_TAG is the only required structure, so "forms" must be modals, not forum posts.
