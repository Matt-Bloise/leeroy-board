# Runbook: feature flags (Cloudflare Flagship)

Decision (Uncle Jimmy, Nov 3): feature flags live in **Cloudflare Flagship**, not in `infrastructure/wrangler.toml` `[vars]`. A flag is **created by the production deploy with wrangler** (disabled) when it is missing, and **flipped by the owner** in the Cloudflare dashboard (Compute, Flagship) or with `wrangler flagship flags enable`. CI never enables, updates, disables or deletes a flag. A flip takes effect without a deploy.

## How it fits together

- `infrastructure/wrangler.toml` binds the Worker to the production Flagship app (the app was created by hand in the dashboard):

  ```toml
  [[flagship]]
  binding = "FLAGS"
  app_id = "1f0b836c-4929-4728-8bee-6b8bde677e79"
  ```

  The app id is an identifier, not a secret. Nothing in CI edits, enables, disables or deletes flags; the production deploy only creates the missing ones (next section).
- The Worker reads a flag with `await flagOn(env, "D1_FEED")` (`infrastructure/worker/flags.js`). With the binding it asks Flagship (default `false`). A **missing flag, a disabled flag, any error, any answer other than `true`, or no answer within 100 ms (`FLAG_TIMEOUT_MS`) means off**. The `[vars]` value is not consulted when the binding exists.
- Without the binding (local dev, unit tests, PR preview Workers) it reads the legacy `[vars]` value of the same name (`D1_FEED = "off"` / `"on"`). `wrangler.toml` keeps `D1_FEED = "off"` as that fallback.
- **PR previews never bind to the production app.** Preview Workers are deployed from the same `wrangler.toml`, so the preview deploy step runs `tools/strip-flagship-binding.mjs` on the patched copy before `wrangler deploy` (it removes `[[flagship]]`, `[flagship]` and `[[env.NAME.flagship]]` blocks, and fails the step if a flagship binding is left in a form it cannot remove, such as `flagship.binding = ...` or an inline `flagship = [...]`, or if `wrangler.json` / `wrangler.jsonc` exists next to `wrangler.toml`, because wrangler reads those first). Previews therefore keep the legacy `[vars]` and stay deterministic. `tests/unit/workflow-secrets.test.mjs` fails if any non-production job can run `wrangler deploy` without stripping first.
- Local `wrangler dev` has the binding and uses wrangler's local Flagship simulator (it does not read the production app unless `remote = true` is added), so set a local flag in the simulator, not `.dev.vars`, to turn a migrated flag on locally.

## The deploy creates missing flags (disabled)

- `infrastructure/flagship-flags.txt` is the one list of flag keys (one per line). `tests/unit/flags.test.mjs` fails when a key passed to `flagOn()` in `infrastructure/worker` is not in it, or when a key in it is not in the table below.
- The **production deploy only** (`.github/workflows/deploy-cloudflare.yml`, master, environment `production`), in the step after `wrangler deploy`, runs `tools/flagship-ensure-flags.mjs`. It reads the app id from `infrastructure/wrangler.toml`, runs `wrangler flagship flags list <APP_ID> --json --all --remote` (read only), and for each listed key that is **absent** runs `wrangler flagship flags create <APP_ID> <KEY> --disabled --remote`.
- A flag created this way is a boolean flag (on = true, off = false, default variation `off`) and is **disabled**, so it serves `off` until the owner enables it. **An existing flag and its on/off state are never touched**: the script never runs enable, update, disable, split, rules or delete.
- The step is `continue-on-error: true` with `timeout-minutes: 3`, and every wrangler call has a 60 s timeout, so a hung wrangler cannot hold up the secrets sync after it. If the list cannot be trusted as the complete list (the command fails or times out, the output is not recognised or is ambiguous, or it shows another page: a non-null `cursor` / `next`, or `has_more` true) it creates nothing; any problem is a yellow `::warning title=Flagship flags::` annotation in the run, never a failed deploy. The API token is never printed.
- PR previews never run it: `tests/unit/workflow-secrets.test.mjs` fails if any workflow other than the production deploy references the script or `wrangler flagship flags create/enable/...`.
- Check it by hand without changing anything: `node tools/flagship-ensure-flags.mjs --dry-run` (lists the real app, creates nothing; needs `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`).

## ASK_RESEARCH provider order, guards and the Claude token cap

> **Superseded under `ASK_RESEARCH` for members:** the order "Claude, then Workers AI, then library facts" below is replaced by "Claude (Sonnet-class compose, Haiku-class retry), then the honest degraded line plus library facts". A member's friend text never reaches Workers AI. See the next section. The tokenising and guard text in this section describes `RESEARCH_NAMES = "tokenised"`, which keeps it exactly.

With `ASK_RESEARCH = "on"` (never in a PR preview) the `/ask` model call runs this chain and nothing else. Gemini, Groq, Cerebras, GitHub Models and OpenRouter never see friend text, and the asker's chosen provider is ignored.

1. **Claude**, only when `anthropicAvailable(env)` (BYOK, Secrets Store binding or legacy secret; `worker/ai-keys.js`) and the monthly token budget allows. Model chain: **compose always runs on `RESEARCH_CLAUDE_MODEL_DEEP` (Sonnet-class, `claude-sonnet-5-5`); the ask's `deep` flag does not pick the model in research mode.** `RESEARCH_CLAUDE_MODEL_FAST` (Haiku-class, `claude-haiku-5-5`) is the overload fallback (and the future understand step; not built). At most **2 Anthropic sends per ask**: compose, then ONE of (a) the 4.5 id of the same family (`RESEARCH_CLAUDE_FALLBACK_DEEP`, `claude-sonnet-4-5-20250929`) on a model-not-found answer (404 not_found_error or 400 naming a missing model), or (b) the Haiku-class model on a 529, any 5xx or a timeout. 401, 403, 400 credit errors, 429 and every other 4xx never retry. Compose gets its own 16 s fetch timeout inside the 22 s Claude budget (the ask hard end; see `splitBudget` in `research/claude.js`; measured in workerd: 16 s with and without an AI Gateway; the gateway's 0.6 share applies only to the legacy gateway-then-direct path, never to these single-hop sends), so a compose timeout still leaves the Haiku-class send at least 2500 ms; a retry whose reservation write used up that time is skipped, its reservation refunded, and Workers AI answers. **The whole Claude hop (reservation writes included) is clamped to the ask's hard end** (`hardEndMs(askDeadlineMs(env))` from `research/no-wall.js`; `ASK_DEADLINE_MS` is the one deadline value for discord.js, the Workers AI hops and the Claude hop): it is skipped with under 2.5 s left, compose gets `min(16 s, time left - 2.5 s)` (everything left when there is no room for a retry), the retry `min(8 s, time left)` and is skipped under 2.5 s, and a reservation write that eats the budget is refunded. **Before turning the flag on, measure real Sonnet-class compose latency** (p50 and p95 for a 700-token answer from the Worker's region) against the 6 s compose timeout: if p95 is near 6 s, compose times out and every such ask pays the Haiku-class retry; raise `CLAUDE_COMPOSE_MS` (and `CLAUDE_TIMEOUT_MS`) only with that data. This has not been measured. **Token restore rule:** a model reply token restores to a display name when it is this request's exact token, or a `{P<n>.xxxx}` whose nonce has the shape of a real nonce (4 characters, a digit 0-7 first and third, any case; the generator always produces that) and whose index is in the request's map. A nonce the asker typed (their text is escaped to brackets) never restores, and ordinary brace text such as `{P2.5}` or `{P1.name}` is not restored (it becomes "someone" and the reply is dropped). The restore is one pass: a restored name is never re-scanned. **Cost if the 5-5 ids do not exist:** each ask then spends 2 Anthropic sends (the 5-5 id answers not-found, the older same-family id answers), so the call count and latency double until `RESEARCH_CLAUDE_MODEL_DEEP` is set to an id that exists.  If both fail, Workers AI answers, then library facts. Spend: the failed compose send keeps its reservation (possibly billed); the Haiku-class retry reserves its own estimate under the same cap and pause rules (refused by the cap means Workers AI, with the one alert row) and settles to its own usage; a retry that fails with a not-billed 4xx refunds only its own reservation. `RESEARCH_CLAUDE_FALLBACK_FAST` is unused in this chain (the Haiku-class send is never itself retried) and stays declared in `wrangler.toml` because `tests/unit/ask-research-claude.test.mjs` pins the declared values (left in place rather than removed); no new vars were added. The 5-5 ids and all prices are **unverified**; check the provider's model list before the first real call. `max_tokens` 700, gateway cache skipped, no friend text in `cf-aig-metadata`. The legacy `CLAUDE_MODEL_*` vars are untouched and serve the flag-off path.
2. ~~**Workers AI** (inside Cloudflare), with the same tokenised prompt.~~ Superseded: removed for members (a guest keeps this hop, tokenised).
3. ~~**Library facts** plus the honest line, or the honest line alone.~~ Superseded by the degraded line (next section), which still carries library facts for a library lookup.

**Tokenised by construction.** Before any model sees the prompt, the system prompt, the party and build blocks, the asker line, the question and the previous turn go through `privacy/tokenise.js`: roster names become per-request tokens (`{P3.k7f2}`); the roster is `privacy/roster-config.js` (a view of `bot-data.js` `ROSTER_DATA`; `genericAliases` lists the plain-word aliases left alone). Replies are detokenised to **display names only**. A reply naming a first name, character or guild name, or carrying a bare or foreign token, is discarded and Workers AI answers instead (then the library facts).

**Guards before every Claude call.** `guardUserText` (strict) runs over EVERY friend-writable segment, after tokenising: the question, the previous turn, every structured sheet field, every sign-up key and value, and the tonight title (each party segment on its own). `guardBody` (cheap) runs over the final request body, which also covers the persona and library text (a CI test, `tests/unit/ask-research-claude.test.mjs`, checks that no library page file holds a roster key; the default persona lives in D1 and is covered by tokenising plus `guardBody`). A hit, a roster that cannot be parsed, or a tokeniser error means no Claude call: Workers AI answers the same tokenised prompt. Never a refusal. The reason is a fixed code appended to the `ask_turns.model` label (for example `claude:claude-haiku-5-5+research` or `workers-ai:...+research [guard:name]`); codes are `guard:<kind>`, `guard:config`, `tokenise:error`, `cpu:budget`, `claude:cap`, `claude:counter-error`, `claude:paused`, `claude:reply-flagged`, `claude:http-<status>`, `claude:timeout`, `claude:error`. No name, text or id is ever in a code.

**Names the Worker knows.** The name list for tokenising and guarding is `ROSTER_DATA` plus, at request time, every sheet in the party document: its name, its slug and any character names (`character`, `main`, `alts`, `characters` on the sheet or in its fields). A sheet that matches a roster member adds its extra names to that member; any other sheet becomes a member of its own. A name that collides with another member, is one character long or is a reserved word is skipped (the owner of the colliding key already protects it). The compiled name map is cached per isolate for each roster and party; only the nonce changes per request.

**Sheet fields: structured vs free-text.** `worker/research/claude.js` (`STRUCTURED_FIELDS`, `FREE_TEXT_FIELDS`, `classifyField`). A structured field that fails the strict guard stops Claude for that ask. A free-text field that fails it is removed from the prompt (Claude and Workers AI both); one that passes is sent. A field not listed is free-text (the safe default).

| Kind | Fields |
|---|---|
| Structured (sent; a guard hit stops Claude) | `class`, `race`, `spec_path`, `spec_at_40`, `level`, `role`, `professions`, `launch_state` |
| Free-text (sent only if it passes the guard, else dropped) | `plan_zone`, `goals` |

**Monthly spend guard (degrades, never walls).** Before the call an estimate (prompt characters / 3 plus the 700-token answer allowance) is RESERVED with one atomic D1 statement on `kv_state` key `claude_tokens_YYYYMM` (UTC month; a plain integer): it succeeds only while the month is under the cap, so concurrent asks cannot all pass a check-then-act gate (at most one reservation overshoots, by its own estimate). After the call the reservation is reconciled to the real usage: all four `usage` fields (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`), each clamped to 0 to 200,000; a missing block, a non-number or a negative counts as the estimate. A call known not to be billed (a guard stop, a 4xx that is not a rate limit) gives its reservation back. `RESEARCH_CLAUDE_MONTHLY_TOKENS` (`5000000`, both shipped in `wrangler.toml` [vars] and as the code default; a bad or empty value means that default, `0` turns Claude off) is the bound. When the reserve fails Claude is skipped silently, Workers AI answers, and one owner-visible row `alert:claude-cap:YYYYMM` (`{kind, month, cap}`, no names) is written once per month; read it with `SELECT * FROM kv_state WHERE key LIKE 'alert:claude-cap:%'`. A counter that cannot be read or written skips Claude, and a failed write pauses Claude for 10 minutes in module memory (`claude:paused`), so spend cannot go unrecorded. The research call sends no `cache_control` (no cached friend text) and makes one send per attempt: no gateway-then-direct second send. The fallback model is tried once, and only when the answer says the MODEL is missing (a `not_found_error` naming the model, or an `invalid_request_error` saying it does not exist); credit, auth and rate errors never retry.

**CPU budget.** Tokenising plus the guards are timed with `performance.now()`; over 8 ms for one ask (or a prompt over 60,000 characters, a clock-free proxy, because a Worker's clock may not advance during pure computation) skips Claude for that ask (`cpu:budget`) and Workers AI answers. Measured on a development PC: about 2.5 ms median, 6.6 ms worst case for a hostile 2,000-character question; the Free plan CPU limit is 10 ms, so this is a safety net, not a guarantee.

**Cost bound.** The monthly cap is 5,000,000 tokens (input + output, all four usage fields summed, cache writes and reads counted as full tokens). Prices read at source on 2026-11-15 (https://platform.claude.com/docs/en/about-claude/pricing, prompts up to 100,000 tokens): Sonnet 5.5 costs $2 per million input tokens and $10 per million output tokens; Haiku 5.5 costs $0.10 per million input tokens and $0.50 per million output tokens. Worst case if all 5,000,000 tokens of the monthly cap were Sonnet output: about $50 (all input: about $10). Haiku at most about $2.50. All of it sits inside the owner's $200 monthly credit. The model ids (`claude-sonnet-5-5`, `claude-haiku-5-5`) are still unverified with a live key. A provider-side charge outside the four usage fields (for example a priced tool) is not counted. Change the cap in `wrangler.toml` and deploy.

## ASK_RESEARCH: RESEARCH_NAMES and the degraded chain

Decided by the owner (the friends have consented; Leeroy's voice comes first; the paid Claude API does not train on API data). Everything here is behind `ASK_RESEARCH`; with it off nothing changes (byte for byte, checked by the flag-off differential).

**`RESEARCH_NAMES`** (`wrangler.toml` [vars] only, never Flagship; read only in `worker/research/real-names.js`). Values: `"real"` (the committed value) or `"tokenised"`. Unset or any other value reads as `"tokenised"`, so a deploy that loses the variable behaves as before and never sends more.

| | `real` | `tokenised` |
|---|---|---|
| Names, sheet fields, builds, the asker's turns | sent as written | per-request tokens (privacy/tokenise.js) |
| Name guard (`guardUserText`, `guardBody` name layers) and the whole-prompt name scan | do not run; a name never fails the ask over | run exactly as before; a hit stops Claude |
| Free-text sheet fields | sent | sent only if they pass the guard |
| Reply name check | none (a name is fine) | a name we never sent, or a foreign token, discards the reply |

**Always on, in both modes** (`tests/unit/ask-real-names.test.mjs`):

1. **Host allow-list.** Friend text goes only to `api.anthropic.com` (`/v1/messages`) or the AI Gateway's anthropic route (`gateway.ai.cloudflare.com/v1/<account>/<gateway>/anthropic/v1/messages`); any other URL, scheme, port or userinfo is refused before a send (`guard:host`).
2. **Secrets and ids (best effort, named patterns).** The API key itself, any secret-shaped env value (names containing TOKEN, SECRET, KEY, SALT, WEBHOOK, PASSWORD, ACCOUNT_ID), `sk-ant-` and other API key shapes, `Bearer ` followed by a token-shaped tail (20+ characters with a digit; the word bearer alone is not a secret), Discord bot and `mfa.` tokens, webhook URLs, AWS `AKIA`/`ASIA` keys, JWTs, Slack `xox` tokens, `Authorization: Basic`, and 40+ hex strings. A key or token shape in the asker's own typed text stops the send (`guard:secret`); a hex-shaped string there (40+ hex characters, 12+ distinct, with a letter) is replaced by `[hex]` and the ask goes on. A sheet field holding anything secret-shaped is dropped whole, in both modes, and the ask goes on; a secret-shaped line in a sign-up, the tonight title, library or persona text (real mode) is dropped whole. No partial redaction or marker is left inside a kept field or line. A final scan of the result fails closed on anything left. 15+ digit ids, fullwidth digits included, become `[id]`; the body scan fails closed on any that remain. A secret in a reply discards the reply (`claude:reply-flagged`). Not caught: a typed password in free text, short tokens. `docs/privacy.md` says so.
3. **Pings.** `@everyone` and `@here` (whatever follows them, fullwidth and zero-width forms included; e-mail addresses are left alone) and `<@id>`, `<@&id>` are defanged in what is sent and in the reply (`<#id>` channel links do not ping and are left alone); Discord posts carry `allowed_mentions` none (`discord.js`, unchanged).
4. **Fencing.** Friend text stays inside the `prompt-fence.js` markers (`USER_QUESTION`, `PARTY_STATE`, `YOUR_BUILD`, `PRIOR_TURNS`), the fence tokens are stripped from it, and the system prompt tells the model fenced text is data.

**Chain for a member under `ASK_RESEARCH` (supersedes "Claude, then Workers AI, then library facts").**

1. Claude Sonnet-class compose (`RESEARCH_CLAUDE_MODEL_DEEP`).
2. Claude Haiku-class retry on 529, any 5xx or a timeout (`RESEARCH_CLAUDE_MODEL_FAST`; at most 2 sends per ask, the 4.5 model-id fallback unchanged).
3. If neither answers (no key, monthly cap, guard stop on a secret or host, timeout, error, an unusable or flagged reply): **no Workers AI, no Gemini, no other provider.** The answer is an honest in-voice line (`DEGRADED_ANSWER`), plus the library's own facts when the question matches the library (`DEGRADED_NOTE`). The `ask_turns.model` label ends with `+degraded` (for example `library:degraded-honest-line+research [claude:http-529]+degraded`, `library:degraded-library-facts+research [guard:secret]+degraded`), so a degraded answer is never silent: `SELECT id, model FROM ask_turns WHERE model LIKE '%+degraded'`. Degraded rows are not carried into later prompts as earlier answers. The bracketed reason is a fixed, value-free class: `claude:timeout@compose-16s` or `claude:timeout@retry-6s` (which send timed out and after how many whole seconds, capped at 99), `claude:http-NNN`, `claude:subrequests` (the Workers subrequest limit), `claude:header` (an unusable gateway token or header value), `claude:error-<ErrorName>` (the error NAME only, letters and digits, at most 24 characters; never the message), `claude:cap`, `claude:no-time`, `guard:*`. A bare `claude:error` means the error had no name. `claude:error-ReferenceError` on every ask means a Node-only global (such as `Buffer`) crept into Worker code: the Worker has no `nodejs_compat` (tests/unit/ask-claude-error-class.test.mjs scans for it).

The degraded line depends on the cause (`degradedLines` in `research/provider.js`): a transient cause (timeout, 5xx, 529, rate limit) says it is a brief outage; every other cause (monthly cap, no key, `guard:secret`, `guard:host`, `cpu:budget`, an unusable reply) promises nothing and says what would settle the question. Neither matches the no-walls pattern (`WALL_RE`) or promises a time. Guests never reach Claude and always get the tokenised, field-dropping prompt (the real-mode party text is for members only); Workers AI answers them with the tokenised prompt, then library facts, and a guest whose prompt cannot be tokenised gets library facts only (the raw prompt never goes to Workers AI); they have no friend history, so the owner's decision does not cover them. The admin evaluation (`eval.js`) tokenises its prompt before Workers AI under research (a candidate whose prompt cannot be tokenised fails and nothing is sent). The web path shows the stored reply, which the research finish has already defanged; `allowed_mentions` none applies to Discord posts only. AI Gateway request logging, if switched on in the Cloudflare dashboard, would hold prompts; `cf-aig-collect-log` is not set (not verified against the gateway).

Changed behaviour to watch: with tokenised mode the CPU budget (`cpu:budget`) and every name-guard stop used to fall to Workers AI; they now give the degraded line.

## ASK_RESEARCH: no walls for members (W5), and what guests get

With the flag on, a **member** (a roster member on Discord, or a signed-in web member; membership comes only from the roster or the member key, never from a request body) never meets a wall on `/ask`, the right-click "Ask Leeroy" or the web ask. The per-user daily cap (40), the tenant share, the Workers AI neuron cap and "ask 41" do not refuse; the answer degrades along Claude, Workers AI, library facts. `worker/research/no-wall.js` holds the rules; `answerWithAi` skips the budget verdict for a member, and `/ask` skips its early refusal.

- **One member can spend the whole neuron cap, by design.** Members are not capped against each other. When the day's neurons (8,000 by default, `AI_DAILY_NEURON_CAP`) are gone, every member's Workers AI step stops and the next members get Claude (inside its monthly token cap) or, when Claude is unavailable or capped, library facts with the honest "research hand" line. Nobody is refused; the answers are thinner. The owner sees this in the per-user rows (`ai_budget:<day>:user:<hash>`) and the global row.
- **The per-user counter counts model answers only** (Workers AI or Claude). A library-facts answer, a deadline or a failed ask does not count. It keeps counting past 40 for visibility and never refuses a member.
- **Guests are Workers AI, then library facts only.** An anonymous web visitor or a Discord user not on the roster is never sent to Claude and never touches the Claude token counter. Guests keep their limits (web: 2 per hour per IP; non-roster Discord: the 40 per day cap, with the old refusal text). Guests share one budget row, `ai_budget:<day>:tenant:guests`, capped at 25% of the neuron cap (`GUEST_SHARE_PCT`); the estimate is reserved atomically before each guest Workers AI call, so a flood cannot pass it, and a refused reservation answers from library facts. A guest flood cannot take more than that 25% from members.
- **Member-facing strings** (error line on a deadline, the "thinking" line, the honest research lines) never contain "try again", "limit", "midnight", "back at", "quota" or "too many": persona pack `ackLines` and `errorLines` that read that way are skipped. The only strings allowed to match are the client's typed-length validation message and the guest-only model label (`tests/unit/ask-no-walls.test.mjs`, test 11).
- **Deadline margin.** Every Workers AI attempt in research mode is capped to end 4 s before the 26 s deadline (`researchTimeoutMs`), and the second send after an unusable answer only starts within half the deadline (13 s) of the ask.
- **Non-roster Discord users** keep the 40 a day cap with the old refusal, and that check comes first: a spent guests' share or neuron cap cannot lift it. Under 40, a spent share gets library facts (no model), and each library answer counts toward the 40.
- **The deadline margin follows `ASK_DEADLINE_MS`.** Delivery and research use the same value (default 26 s; the Worker ends waitUntil work 30 s after the response and the Discord edit has a 28 s budget, so do not raise it); the hard end for every Workers AI attempt and the Claude hop is the deadline minus a sixth, at most 4 s. Attempts with under 1 s left are skipped, and with the gateway there is no 1 s floor and no direct run after a failed gateway run unless 1 s remains.
- **A thrown interaction** shows a roster member "Something broke on my side, and I have logged it. Check the board for the answer." (no retry wording) when research is on; everyone else, and flag off, keeps the old text.
- **Known remaining retry wording.** The web client shows "Sending it again is fine." (`scenes/chamber.js` lines 164 and 165, and `js/ask.js` on a failed turn) on an error turn, and the guest rate-limit message ("That is N questions in the last hour...") on a 429. The client ships the same bytes with the flag on or off, so making them flag-dependent would change flag-off output; they are left as they are. The 429 message is only ever sent to guests.
- **Known approximation: the guests' row clamp.** The reservation settles to the real cost clamped to the share. When several reservations are outstanding, a clamped settlement can leave the row slightly under the true spend (a bounded undercount, at most the overrun of the calls in flight; the global row still records the real cost). It is not redesigned.
- Refusals, errors and Off-voted answers are never reused: research mode does not use the 10-minute same-answer reuse at all.

## ASK_RESEARCH: carry-list restores (memory, length, abstain, advice)

These four restores from the original bot apply only with `ASK_RESEARCH` on. With it off the prompt, the stored answer and the D1 reads are byte-identical to before (checked by the flag-off differential against `origin/master`: 2,880 runs, 0 differences).

- **Conversation memory.** `worker/research/turns.js` reads the asker's own last 3 answered turns from `ask_turns` in one D1 query, scoped by the salted asker hash in `ask_turn_askers` (a visitor has none; another person's rows never match). A public ask sees only public turns. Rows older than 24 hours, unanswered, errored, budget, outage and abstain rows are excluded, and an erased turn is a deleted row so it cannot match. Each question is capped at 280 characters, each answer at 400, the block at 1,800; links, mentions and footer lines are removed. The block goes into the prompt as a `PRIOR_TURNS` fence and through the tokeniser and the strict guard like the question, so a guard hit stops the Claude call and Workers AI answers. The earlier turns are not added to the grounding text for numbers, only the earlier questions.
- **Length.** The live path already sent 700 tokens and finished at 1,500 body and 1,900 total. What still cut it short was the prompt: a stored persona line "Keep the reply under N characters" with N below 1,500, and the built-in "2 to 4 sentences" line when no persona exists. Under research `RESEARCH_LENGTH_OVERRIDE` replaces both for that ask.
- **Abstain in voice.** The code-written "library does not cover that yet" answer was already unreachable under research (the model answers, and refusal sentences it writes are stripped). The two remaining code-written fallbacks, the outage answer and the member error lines, now name what would settle the question.
- **Advice.** The imperative-opener stripper in `repairHouseVoice` is skipped under research, so "what should I" keeps its plain pick.

Limits: library-grounded research asks still carry the old "Inform, never instruct" voice line, because the research voice rules are added only when the library has nothing. Memory carries the asker's own turns only; channel history needs a separate owner decision.

## GROUP_MEMORY: the group's memory for the research path

`GROUP_MEMORY` is a `[vars]` flag, read with `legacyOn` (only the word `on`, any case, trimmed) and shipped `off`. It has an effect only when `ASK_RESEARCH` is also on, and never in a PR preview (research mode is never on there). Full description, the flip and the rollback: [`group-memory.md`](group-memory.md).

- **Off or unset: no D1 read, no D1 write, no prompt text, no cron work.** The ask row, the Claude request and the cron are byte for byte what they were (checked by the flag-off differential against `origin/master`, see the PR). Erase and export cover the two new tables whether or not the flag is on.
- **On:** a roster member's answered ask is filed in `group_log` (one INSERT); the member's research prompt gets one fenced `GROUP_MEMORY` block (wiki pages about the asker and the people named, plus the last 12 rows of the channel, at most about 3,500 characters) when `RESEARCH_NAMES` is `real`; the 6-hour cron runs the wiki refresher (one Haiku-class call, at most 60 rows, when 10 new rows or 24 hours have gathered).
- **Token cap and cost.** The monthly cap is 5,000,000 tokens (`RESEARCH_CLAUDE_MONTHLY_TOKENS`). The refresher reserves and settles in the same `claude_tokens_YYYYMM` counter as compose, and ALSO in its own counter `claude_tokens_group_YYYYMM` against a sub-cap of 10% of the monthly cap (500,000 tokens), so asks always have room. At most 2 runs a day (a per-day counter in the `group_wiki_state` row), one lock row so two runs never both call, and after a failure no second try until the next UTC day. Worst case for one run: at most 6 pages of 2,000 characters plus 60 rows of 400 characters plus the instructions, roughly 40,000 characters or about 13,000 tokens at the reservation's 3 characters per token, plus the 5,000-token reply allowance: about 18,000 tokens reserved, settled to the real usage. Two runs a day is about 36,000 tokens a day and about 1.1 million a month at the worst size, so the 500,000 sub-cap is the binding bound: at most about 27 worst-size runs a month, then the refresher skips (`claude:subcap`) until the month rolls over. Prices read at source on 2026-11-15 (https://platform.claude.com/docs/en/about-claude/pricing, prompts up to 100,000 tokens): Sonnet 5.5 costs $2 per million input tokens and $10 per million output tokens; Haiku 5.5 costs $0.10 per million input tokens and $0.50 per million output tokens. Worst case if all 5,000,000 tokens of the monthly cap were Sonnet output: about $50 (all input: about $10). Haiku at most about $2.50. All of it sits inside the owner's $200 monthly credit. The model ids (`claude-sonnet-5-5`, `claude-haiku-5-5`) are still unverified with a live key. At the Haiku rates the whole 500,000-token sub-cap costs at most about $0.25 even if all of it were output.

### SHADOW_ASK limits: `SHADOW_ASK_LIMITS`

ONE `[vars]` value, `SHADOW_ASK_LIMITS = "hourly/daily/percent"` (for example `"60/100/5"`), bounds the shadow route (`shadow-ask.md`). It is one variable because the Workers Free plan allows only 64 variables in all (text plus secrets): the three separate vars pushed the Worker to 65 and every deploy failed; `tests/unit/var-budget.test.mjs` now fails in the PR when the budget is exceeded. Absent means the defaults 6/20/2. They are not flags (no Flagship key, no on/off); a change is a `wrangler.toml` edit and a deploy.

| Part of `SHADOW_ASK_LIMITS` | Default | Range | Meaning |
|---|---|---|---|
| part 1 (hourly) | `6` | integer 1 to 120 | accepted calls per rolling hour |
| part 2 (daily) | `20` | integer 1 to 600 | accepted calls per rolling day; never below the hourly value |
| part 3 (percent) | `2` | number 0.1 to 20 | the shadow's own share of `RESEARCH_CLAUDE_MONTHLY_TOKENS`, in percent |

Unset, empty, non-numeric, `NaN`, `Infinity`, zero, negative or exponent-form (`1e3`) values fall back to the default, never to unlimited. A positive value outside the range is clamped to the nearest edge. The monthly cap and the always-on guards apply regardless.

## Migrate another flag

1. Add the **same key as the var** (for example `CARDS_ENABLED`) to `infrastructure/flagship-flags.txt`; the next production deploy creates the boolean flag, disabled.
2. In the Worker replace the read of `env.NAME` by `await flagOn(env, "NAME")` and keep `NAME = "off"` in `[vars]` as the fallback.
3. Add the key to the table below (`tests/unit/flags.test.mjs` checks that every key passed to `flagOn` is in the key list and listed here, and has an off fallback).
4. Deploy (the flag is created disabled), then turn it on in the dashboard or with `wrangler flagship flags enable <APP_ID> <KEY> --remote`.

## Flip a flag

Cloudflare dashboard, Compute, Flagship, app `leeroy-brain`, the flag, toggle **enabled** (or serve `on`), or `wrangler flagship flags enable <APP_ID> <KEY> --remote`. A disabled flag serves its default variation, `off`. Only a person does this; the deploy never does.

## Roll back

**Flip the flag off in the dashboard. No deploy.** If Flagship misbehaves the Worker treats the error as off. To drop the binding entirely, redeploy a previous Worker version (docs/runbooks/rollback.md); then the Worker uses `[vars]`.

## DEADMAN: the dead-man check

`DEADMAN` is a `[vars]` flag shipped `off`; only the exact value `on` turns it on (anything else reads as off). It is never on in a PR preview and needs `DISCORD_BOT_TOKEN` (16+ characters): the heartbeat keys (one per source, plus a read-only status key) are derived from it with their own labels, so there is no separate secret. Off: `POST /api/heartbeat` and `POST /api/heartbeat/status` answer 404, the one-minute cron step returns at once, and nothing is read or written. On: signed heartbeats are recorded in `kv_state` key `heartbeat`, and the cron opens a row in `incidents` for a source silent longer than `DEADMAN_STALE_SECONDS` (default `300`, clamped to 120..3600). `DEADMAN_EXPECT` (default empty) lists sources expected before their first heartbeat. Nothing is sent anywhere: alerting is not built and would be a separate flag, `DEADMAN_ALERT`, decided later. Detail: `deadman.md`.
